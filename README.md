# keep-going

一个给 Codex 用的 skill。

它的目标很直接：当任务比较长、步骤比较多、或者需要连续推进时，让 Codex 默认持续执行，直到任务完成，或者遇到真正的阻塞为止。它不是让模型“更激进”，而是把默认交互方式从“经常停下来问要不要继续”改成“先做完下一段有意义的工作，再汇报结果”。

## 这是什么

`keep-going` 会把当前请求视为一次明确授权：

- 在用户给定范围内持续推进任务
- 优先做进度更新，而不是频繁请求确认
- 能直接判断的事，直接判断
- 能本地验证的事，尽量先验证
- 只有遇到真实阻塞，才停下来提问

这个 skill 适合编码、调试、重构、迁移、排障、研究、长链路修复这类任务。

## 适用场景

下面这些场景很适合用 `keep-going`：

- “把这个 bug 修到能过测试为止。”
- “别一小步一确认，直接做完再汇报。”
- “继续查这个问题，除非真卡住。”
- “先把能改的都改掉，再告诉我还有什么风险。”
- “从分析到实现到验证，整条链路走完。”

如果任务本身就是开放式讨论、方案比较、产品决策、或者必须由人拍板的业务选择，这个 skill 仍然会工作，但它会在真正需要你决定的时候停下来问。

## 核心行为

`keep-going` 的行为重点如下：

1. 快速建立目标、约束和工作阶段。
2. 在本地上下文足够的前提下做合理假设，不为了小偏好中断任务。
3. 至少完成下一块“有意义的工作”再回来汇报，而不是每一步都停。
4. 尽量把相关的读取、修改、检查、验证批量完成。
5. 在可行时先做验证，再结束当前回合。

## 它会继续做什么

在风险可控、范围明确时，Codex 会继续做下面这些事，而不是先问你：

- 读取代码、文档、日志、配置和本地产物
- 运行非破坏性的检查命令
- 修改完成任务所需的文件
- 按仓库现有风格做小实现决策
- 在用户没有明确偏好的情况下选择合理默认值
- 从分析直接推进到实现，再推进到验证

## 它什么时候会停下来问你

只有遇到真实阻塞，才应该停下来提问。典型阻塞包括：

- 下一步是破坏性操作，或者难以撤销
- 缺少本地无法推断的关键信息
- 存在多个差异很大的方案，选错会造成明显返工
- 权限、审批、计费、网络、策略边界阻止继续执行
- 用户明确要求在某个节点停下来复核

它不会因为“小命名要不要改”“这个日志要不要顺手清理”“要不要先跑一下测试”这类低成本决策就打断你。

## 安装

仓库根目录提供了安装脚本：

```bash
./install.sh
```

默认会把 skill 安装到：

```text
${CODEX_HOME:-$HOME/.codex}/skills/keep-going
```

如果你之前装过旧名字 `continue-unless-blocked`，安装脚本会在安装新名字后自动清理旧目录，避免本地同时保留两个版本。

## 更新

用仓库最新内容覆盖已安装版本：

```bash
./install.sh --update
```

## 卸载

移除已安装 skill：

```bash
./install.sh --uninstall
```

卸载逻辑也会顺带清理旧名字 `continue-unless-blocked` 的安装目录。

## 如何触发

### 1. 显式触发

最直接的用法是在请求里明确写 skill 名：

```text
$keep-going，继续修这个仓库里的测试失败，直到定位到根因并给出修复。
```

```text
$keep-going，把这个功能从排查、改代码、跑验证一路做完，除非真阻塞别停。
```

### 2. 自然语言触发

这个 skill 允许隐式触发，所以你也可以不用写 `$keep-going`，直接表达意图：

```text
这个任务你一直做，做到完。没有真阻塞不要问我要不要继续。
```

```text
直接往下做，查完、改完、验证完再回来。
```

```text
继续处理，别分很多轮确认。
```

### 3. 作为默认工作风格

如果你经常偏好这种协作方式，可以在任务一开始就明确一句：

```text
后面这个任务按 keep-going 模式执行。
```

这样模型会把整段工作当成长任务来处理。

## 推荐提示词

下面这些提示词通常比较稳：

```text
$keep-going，修复当前失败测试。优先最小改动，做完后跑相关验证。
```

```text
$keep-going，排查这个接口为什么返回 500。先定位根因，再修复，再验证。
```

```text
$keep-going，重构这个模块，但不要改变对外行为。完成后给我风险点。
```

```text
$keep-going，继续迁移这部分代码，除非涉及破坏性操作，否则不要停下来问。
```

## 仓库结构

```text
.
├── install.sh
└── skills
    └── keep-going
        ├── SKILL.md
        └── agents
            └── openai.yaml
```

文件作用如下：

- `install.sh`
  安装、更新、卸载 skill。
- `skills/keep-going/SKILL.md`
  skill 的主体说明和执行规则。
- `skills/keep-going/agents/openai.yaml`
  agent 展示名、简短描述、默认提示词，以及是否允许隐式触发。

## 旧名字迁移

这个 skill 之前的名字是：

```text
continue-unless-blocked
```

现在改成了更短的：

```text
keep-going
```

对应变化：

- skill 名从 `$continue-unless-blocked` 改为 `$keep-going`
- 目录从 `skills/continue-unless-blocked` 改为 `skills/keep-going`
- 安装目录从 `~/.codex/skills/continue-unless-blocked` 改为 `~/.codex/skills/keep-going`

如果你还有旧文档、旧 prompt、旧快捷命令，建议一起替换成新名字。

## 自定义

如果你想调整行为，可以改下面两个文件：

- `skills/keep-going/SKILL.md`
- `skills/keep-going/agents/openai.yaml`

常见自定义方向：

- 改 display name
- 改默认 prompt
- 增减何时继续、何时停下的问题判定
- 增加更偏向你团队习惯的措辞

改完后执行：

```bash
./install.sh --update
```

## 验证安装是否成功

安装完成后，检查目标目录是否存在：

```bash
ls "${CODEX_HOME:-$HOME/.codex}/skills/keep-going"
```

如果能看到 `SKILL.md` 和 `agents` 目录，说明安装基本成功。

然后可以用一条显式指令做烟雾测试：

```text
$keep-going，读取当前仓库结构，总结一下接下来最合理的三步，但不要频繁停下来确认。
```

如果模型表现出“持续推进、少确认、只在真实阻塞时提问”的行为，说明 skill 已生效。

## 设计目标

这个 skill 的目标不是替代人判断，而是减少低价值确认。

它希望达到的协作体验是：

- 该自己判断的，自己判断
- 该继续执行的，继续执行
- 该做验证的，先做验证
- 真有风险或真缺信息，再回来问用户

如果你偏好“先做完一段，再汇报；不是每一步都确认”的工作方式，这个 skill 就是为这个场景准备的。
